# Gusto Design Lab

Bibliothèque séparée de composition et de rythme : [Références structurelles](STRUCTURAL_REFERENCES.md). Ingestion URL, capture sécurisée, analyse Vision et interface admin ; aucun branchement au moteur artistique actuel.

La génération Homepage V2 utilise désormais un journal séparé, des checkpoints PNG par chapitre et une finalisation idempotente. Voir [HOMEPAGE_V2_RECOVERY.md](HOMEPAGE_V2_RECOVERY.md) pour les actions de reprise/finalisation, la compatibilité, le secours disque et les limites de coût. Les variations gardent leur chemin existant.

Interface admin : `/dashboard/admin/sites`, `/dashboard/admin/sites/references` et `/dashboard/admin/sites/portfolio`.
API privée : `/api/admin/design-lab/*` (JWT admin, rôle `admin`). Aucun champ Design Lab n'est ajouté au document public `Restaurant`.

## Configuration

- `OPENAI_API_KEY` : obligatoire pour l'analyse et la génération, côté serveur seulement.
- `OPENAI_DESIGN_REFERENCE_ANALYSIS_MODEL` : défaut `gpt-6-luna`, analyse économique des inspirations, suggestions de tags et synthèse documentaire du site existant ; Responses API, Structured Outputs, `reasoning.effort=low`.
- `OPENAI_DESIGN_DIRECTION_MODEL` : défaut `gpt-6.1-sol`, réflexion créative et directions A/B/C ; Responses API, Structured Outputs, `reasoning.effort=high`.
- `OPENAI_DESIGN_IMAGE_GENERATION_MODEL` : défaut `gpt-image-2.5-flare`, premières maquettes et exploration rapide. Ce modèle est aussi utilisé sur l'endpoint Images Edits si une première maquette utilise des assets du restaurant.
- `OPENAI_DESIGN_IMAGE_EDIT_MODEL` : défaut `gpt-image-2.5-sunburst`, variations et retouches fidèles avec l'image parente en entrée de l'endpoint Images Edits.
- `OPENAI_DESIGN_IMAGE_QUALITY` : défaut `high`. Valeurs configurables `low`, `medium`, `high`, `xhigh`, `max` si le modèle choisi les prend en charge.
- `GUSTO_DESIGN_LAB_DEBUG_PROMPT=true` : en développement uniquement, affiche dans les logs le prompt exact de chaque chapitre de maquette. La variable est ignorée si `NODE_ENV=production`.
- Cloudinary existant : `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`.
- Capture Portfolio : `GUSTO_PORTFOLIO_CAPTURE_ENABLED=true` autorise explicitement les captures dans l'environnement concerné. Variable absente ou différente de `true` : capture désactivée (valeur recommandée pour un exemple de configuration : `GUSTO_PORTFOLIO_CAPTURE_ENABLED=false`). `playwright-core` utilise le Chrome local uniquement lorsque la capture est autorisée ; `GUSTO_PORTFOLIO_CHROME_PATH` permet d'indiquer son exécutable si aucun chemin standard ne convient.

Les appels OpenAI sont centralisés dans `services/design-lab/openai.service.js`. Les uploads et la présélection locale sont dans `services/design-lab/design-lab.service.js`. MongoDB stocke URL et `publicId` des fichiers Cloudinary. La racine des nouveaux uploads, centralisée dans `services/design-lab/cloudinary-folders.js`, est `Gusto_Workspace/design-lab`. Elle contient `references/`, `projects/<projectId>/assets/`, `generations/` et `portfolio/<portfolioSiteId>/`. Les anciens `publicId` restent acceptés pour lire ou supprimer les images déjà enregistrées ; aucun déplacement Cloudinary ou changement MongoDB n'est automatique.

L'environnement Cloudinary vérifié le 2 octobre 2026 utilise les dossiers dynamiques. Dans ce mode, déplacer les dossiers depuis la Media Library ne change ni les `publicId` ni les URLs de livraison ; les anciens `publicId` peuvent donc conserver leur préfixe `gusto/design-lab` après le déplacement. Vérifier que le déploiement utilise le même environnement Cloudinary avant de déplacer ses assets.

Avant l'upload, `sharp` convertit les références JPEG, PNG et WebP en véritables fichiers WebP de qualité 85. La largeur maximale est 2 000 px, sans agrandissement ni recadrage ; le ratio est conservé. Les captures de homepage longues gardent toute leur hauteur, avec une réduction proportionnelle uniquement si la limite technique de 16 383 px par côté du format WebP l'impose. Les assets JPEG/PNG suivent la même règle ; les logos et autres éléments graphiques identifiés sont encodés en WebP sans perte pour préserver leurs contours et leur transparence. Un asset déjà en WebP et aux dimensions adaptées est conservé tel quel. Les SVG ne sont pas acceptés par cet upload et ne sont jamais convertis. Les maquettes générées sont conservées dans leur format de sortie pour éviter de dégrader les éditions suivantes. Cloudinary reçoit donc les octets WebP des références et assets raster après conversion locale, et non uniquement une URL de transformation.

Ce découpage réserve le raisonnement plus coûteux aux directions artistiques, exécutées quelques fois par projet. Luna traite les références en volume ; Flare sert les premières explorations visuelles ; Sunburst est réservé aux éditions où la fidélité à la maquette existante compte davantage. Aucun modèle n'est choisi dans les routes. `OPENAI_API_KEY` reste exclusivement dans le `.env` serveur et peut être vide : le serveur démarre, puis signale une erreur explicite à la première action IA.

## Données et workflow

`SiteProject` contient le brief, les services, les quatre curseurs, les styles, les assets et leurs rôles, les références sélectionnées, les directions et l'historique des générations. L'admin associe éventuellement le projet à un vrai restaurant Gusto au moyen du sélecteur existant ; l'API vérifie que ce `restaurantId` existe. `selectedGeneration` désigne la version regardée. Chaque variation conserve `parentGenerationId`, instruction libre, prompt effectivement envoyé et image. Les générations récentes gardent aussi `assetsUsed`, `generationStrategy` (chapitres et assets par chapitre) et `outputDimensions` ; le snapshot d'approbation reprend le même sous-document. `DesignReference` contient capture, `manualTags`, `visualTags`, `businessTags`, analyse structurée, caractéristiques et sections inspirantes. Les tags manuels sont éditables dans l'admin et conservés à la réanalyse. Les deux catégories IA sont remplacées intégralement et dédupliquées par rapport aux tags manuels et entre elles. Une référence est analysée à l'import puis seulement sur demande de réanalyse.

L'approbation met `status=approved`, `approvedGeneration` et `approvedAt`, et persiste `approvedSnapshot`. Ce snapshot fige le projet, le brief, le contexte documentaire, les réglages, les assets, la direction, le Style Frame validé, la génération et les références utilisées. Il constitue le contrat final stable pour la future Site Factory tant que le projet est approuvé. Toutes les mutations du projet sont refusées dans cet état ; les consultations restent possibles. `POST /api/admin/design-lab/projects/:id/reopen` déplace le snapshot vers `approvalHistory`, remet le statut à `exploration` et efface les pointeurs d'approbation courants sans effacer les générations. Une nouvelle approbation crée un nouveau snapshot.

`brief.existingWebsite` reste l'URL du site précédent, séparée de la bibliothèque d'inspiration. Depuis le brief, l'admin peut déclencher `POST /api/admin/design-lab/projects/:id/existing-website-context` après avoir enregistré l'URL. Le serveur charge la homepage HTML, découvre ses liens internes du même domaine et retient au plus six pages supplémentaires. Les chemins, libellés et liens de navigation liés au restaurant, son histoire, son équipe, sa carte, au traiteur, aux événements, aux groupes ou aux informations pratiques sont prioritaires. Pages légales, actualités individuelles, PDF, réseaux sociaux, pages de connexion, liens externes et URL à paramètres sont écartés. Il ne suit pas les liens des pages secondaires.

Chaque requête vérifie l'adresse publique après résolution DNS, fixe cette adresse pour la connexion et revalide chaque redirection. Le nombre de pages, les redirections, le temps, la taille par page et la taille totale envoyée au modèle sont limités par les constantes de `existing-website.service.js` (`MAX_PAGES = 7`, dont la homepage). Les scripts, CSS, navigation et bandeaux de cookies sont retirés du texte ; le footer n'est conservé qu'une fois, sur la homepage. Les pages presque identiques et les blocs répétés sont dédupliqués. Une page secondaire en erreur est ignorée et comptabilisée ; une homepage sans texte suffisant produit une erreur claire, notamment pour un site rendu uniquement en JavaScript. Aucun navigateur ni fallback de rendu JS n'est lancé.

Un seul appel au modèle économique d'analyse synthétise tous les extraits textuels. `existingWebsiteContext` contient `restaurantSummary`, histoire, positionnement, cuisine, chef, équipe, services, spécialités, valeurs, faits notables, lieu, contact, horaires, contenu utile, `sourcePages` (`url`, `pageType`), nombres de pages découvertes/en erreur et date d'analyse. Ni HTML brut, ni textes complets, ni capture ne sont stockés. Une réanalyse efface d'abord atomiquement l'ancien contexte, puis enregistre le nouveau seulement en cas de succès ; un échec ne laisse donc pas une ancienne synthèse exploitable. Changer ou supprimer l'URL efface aussi le contexte. Le brief manuel reste prioritaire. Les directions ne reçoivent que les faits documentaires si une URL de site existant est encore enregistrée, sans URL source ni `sourcePages`, avec interdiction explicite d'en déduire un style visuel, même si un fait mentionne une couleur de la salle. Le moteur de sélection des références et le prompt direct des maquettes ne lisent pas l'ancien site.

L'analyse d'une référence classe d'abord l'image (`raw_webpage`, `webpage_in_presentation`, `design_case_study`, `other`) et consigne temporairement les `presentationArtifacts` (`type`, `description`, `shouldIgnore`) dans la réponse structurée OpenAI. MongoDB ne garde que `referenceType` et une courte liste `artifactTypes` ; les descriptions de la planche ne sont pas stockées. Le prompt demande d'isoler visuellement la page réelle avant d'en décrire le style, sans considérer les mockups de device, cadres fictifs, annotations, fonds de présentation ou captures secondaires comme des éléments du site. Il précise qu'un élément inhabituel peut néanmoins appartenir à la page selon le contexte. Une protection locale retire les mentions d'artefacts explicitement détectés des tags, de l'analyse et des caractéristiques. Le schéma structuré produit séparément `visualTags` (langage visuel) et `businessTags` (contexte métier). Les références classées `other` sont exclues de la sélection. Le score local privilégie fortement `visualTags` ; `businessTags` est seulement un bonus secondaire, sans pénalité pour une autre cuisine. Les directions reçoivent les principes visuels séparément du contexte métier d'origine, ainsi que les tags manuels pertinents, sans descriptions d'artefacts.

Migration appliquée à la base de test le 1er octobre 2026 : les 14 références conservent leurs noms, images Cloudinary, sources, tags manuels, analyses compatibles et métadonnées. Leurs anciennes listes IA non classées ont été retirées et `visualTags` et `businessTags` initialisés à `[]`, sans deviner la catégorie des anciens tags. Les anciens champs génériques et descriptions d'artefacts ont été supprimés. Le script ponctuel de l'ancienne structure a été supprimé après cette migration. Les 14 références, dont REF 01, REF 02 et REF 03, doivent être réanalysées pour remplir les nouvelles catégories. L'admin propose « Réanalyser les références » : les appels sont séquentiels, avec progression et bilan des erreurs ; une analyse individuelle reste possible. La migration elle-même n'a appelé ni OpenAI ni Cloudinary.

Le moteur classe les références actives et analysées localement avec les styles et les scores de densité, asymétrie, chevauchements et vide. Jusqu'à huit résumés créatifs compacts, sans images, alimentent l'étape des territoires ; les expansions ne reçoivent que les analyses détaillées de leurs références pressenties. Les quatre curseurs sont transmis aux prompts et influencent explicitement la sélection ou les contraintes créatives. Les prompts interdisent les compositions web génériques courantes et exigent trois approches distinctes, tout en préservant lisibilité et accès à la réservation.

## Portfolio Gusto — architecture d'exécution

La capture et l'analyse visuelle sont des actions admin ponctuelles, autorisées uniquement si `GUSTO_PORTFOLIO_CAPTURE_ENABLED=true` sur le **serveur qui reçoit la demande**. Sans cette valeur exacte, `POST /api/admin/design-lab/portfolio/:id/analyze` répond immédiatement `403` avant de créer un travail. L'API expose `portfolioCaptureEnabled` dans les réponses de liste et de détail ; l'admin désactive le bouton de capture quand la capacité est absente. La création d'une fiche, sa lecture et son activation ne déclenchent aucune capture.

Dans l'organisation actuelle, le backend lancé localement sur le Mac depuis `main` peut recevoir ce flag et utiliser le Google Chrome déjà installé. Il écrit les captures WebP dans Cloudinary partagé et les pages, URLs Cloudinary, tags visuels, analyses, `visualProfile`, compteurs et date d'analyse dans MongoDB de production. Les autres branches peuvent utiliser le même flag avec leur base de test. Le choix de la base reste celui de la configuration MongoDB existante ; aucun transfert entre bases n'est réalisé. Les captures sont traitées en mémoire et ne créent pas de fichier screenshot temporaire à conserver.

Render garde le flag absent ou à `false` : il ne lance pas Playwright pour le Portfolio et n'a besoin d'aucun Chrome ni d'installation de navigateur au build. Il lit les documents MongoDB et les URLs Cloudinary déjà persistés. La sélection et la génération des directions calculent le résumé Portfolio en Node à partir des `visualProfile` des sites actifs analysés, après exclusion du restaurant courant. Ce calcul ne réanalyse aucun site, ne lit aucun screenshot et n'appelle ni Playwright ni Luna Vision. Sol peut recevoir ce résumé textuel lors de la génération des directions. Le Mac peut être arrêté une fois l'analyse terminée.

## Trois flux distincts

- **Existing website** : `SiteProject.brief.existingWebsite` et `existingWebsiteContext` décrivent le restaurant courant par extraction de texte. Aucun élément visuel du site précédent n'entre dans la sélection ou le prompt créatif.
- **DesignReference** : bibliothèque externe d'inspirations visuelles, source de principes artistiques transposables. Aucun site du Portfolio n'est créé automatiquement comme référence.
- **GustoPortfolioSite** : sites déjà réalisés par Gusto, utilisés seulement pour comparer le langage visuel existant et éviter la répétition. Le modèle ne stocke ni histoire, ni carte, ni prix, ni coordonnées, ni horaires. Il conserve l'URL publique, le nom, le slug et restaurantId facultatifs, l'état actif, les pages et leur analyse, `visualProfile` et les dates.

L'admin ajoute un site dans « Portfolio Gusto », puis déclenche explicitement « Capturer et analyser ». Les routes admin privées `GET/POST /portfolio`, `GET/PATCH/DELETE /portfolio/:id` et `POST /portfolio/:id/analyze` sont sous `/api/admin/design-lab`. L'analyse part en arrière-plan : l'interface affiche son état et actualise le détail, dont le nombre de pages découvertes et échouées (`captureStats`). Une réanalyse redécouvre les pages, remplace captures, tags et profil, puis supprime les anciennes captures Cloudinary une fois le nouveau document enregistré. Une page interne défaillante est ignorée ; la homepage doit réussir. Désactiver un site le retire de la comparaison sans effacer ses données. Supprimer un site retire aussi ses captures.

La progression Portfolio est persistée dans `GustoPortfolioSite.progress` et relue par le polling déjà présent sur `GET /portfolio/:id`, y compris après un rafraîchissement. Elle contient statut, étape, page courante, total découvert, pages terminées et échouées, pourcentage et message. Les jalons sont : 0–10 % préparation/découverte, 10–35 % captures effectuées, 35–85 % pages traitées, 85–95 % synthèse, 95–100 % sauvegarde. Le pourcentage reste fixe pendant un appel Luna et n'atteint 100 % qu'après l'enregistrement réussi. Les références utilisent `GET /references/progress/:operationId` pendant leur requête synchrone : leur état court vit en mémoire serveur pendant quinze minutes, sans nouveau job ni appel OpenAI. La réanalyse conserve en outre le verrou `analyzing` déjà stocké sur la référence. Aucun pourcentage n'est calculé à partir du temps écoulé.

La homepage est obligatoire. `MAX_PORTFOLIO_PAGES = 9` limite la capture à huit pages internes supplémentaires. Les liens sont découverts uniquement sur la homepage rendue, avec priorité aux navigations et à des pages représentatives : restaurant/histoire, carte et menus, boissons/vins, chef, traiteur, événements, réservation, actualités, contact et cartes cadeaux. Une page éditoriale présente en navigation peut aussi être retenue si son slug est atypique. Les liens externes, pages légales, connexion, admin, API, paiement, sitemap, PDF, pagination, paramètres d'URL, articles individuels et doublons de template sont ignorés. Une ou deux pages de menu au maximum représentent cette famille ; les autres familles sont limitées à une page chacune (deux pour les pages éditoriales). Des captures aux octets identiques sont dédupliquées avant upload et analyse.

`portfolio-capture.service.js` utilise Chromium via `playwright-core` avec viewport 1440 px, rendu JavaScript et capture `fullPage`. Avant chaque capture, la page attend brièvement ses polices, défile par pas de 70 % du viewport en recalculant sa hauteur, laisse charger et décoder les images visibles, puis revient en haut et se stabilise. Le warm-up est borné à 9 secondes, 90 étapes et 50 000 px de parcours ; la capture reste `fullPage`. Il déclenche les reveals réels sans modifier les classes ni les styles du site. Un site dont les éléments se recachent lorsqu'ils quittent le viewport peut encore produire une capture incomplète ; ce cas demandera un traitement ciblé s'il est rencontré. La réservation est capturée uniquement à l'état public initial ; aucune interaction ou soumission n'est effectuée. Toutes les requêtes du navigateur passent par une interception alimentée par un fetch Node : URL HTTP(S) validée, DNS public vérifié et adresse fixée pour la connexion, redirections revérifiées, navigation limitée au même domaine, méthodes autres que GET bloquées. Service workers et WebSockets sont bloqués. Des limites bornent les ressources, requêtes, redirections et temps de capture. Les captures PNG sont converties localement par `sharp` en WebP qualité 85, largeur au plus 2 000 px, ratio et hauteur conservés, sans crop sauf réduction proportionnelle imposée par la limite technique WebP. Cloudinary reçoit ces octets dans `Gusto_Workspace/design-lab/portfolio/<portfolioSiteId>/`. Luna reçoit l'URL de la capture entière ; la preview de l'admin utilise seulement un cadrage CSS.

Le plafond de 12 requêtes simultanées met les requêtes supplémentaires en attente, dans le délai de capture prévu. Il ne les annule pas dès que le navigateur charge beaucoup de scripts à la fois : cela empêchait parfois l'hydratation React et la révélation des titres de Contact et Réservation. Après le warm-up, les grandes images rendues doivent être chargées et décodées avant le screenshot (attente supplémentaire bornée à 5 secondes). Une image encore absente ou cassée déclenche au plus une nouvelle navigation ; si elle reste absente, la page n'est pas enregistrée comme capture complète.

Chaque page retenue reçoit **un appel Vision** au modèle `OPENAI_DESIGN_REFERENCE_ANALYSIS_MODEL` (défaut Luna) avec Structured Outputs : `visualTags`, structure, hero, composition, rythme, typographie, photographie, couleurs, originalité, identité et motifs utiles. Le prompt s'adapte au type de page. Les analyses détaillées des pages sont conservées. **Un seul appel Luna textuel** regroupe ensuite les formulations synonymes en concepts visuels canoniques et indique les pages qui soutiennent chaque concept. Le serveur déduplique les pages par concept, calcule `pageCount`/`totalPages` dans `patternSupport`, classe chaque concept une seule fois comme dominant (au moins 75 % des pages), récurrent (au moins deux pages) ou ponctuel, puis construit des `visualTags` globaux à partir des concepts partagés. Les motifs fonctionnels, même répétés, ne deviennent pas automatiquement des tags globaux ou des signatures. `signaturePatterns` ne retient que quelques concepts globaux. Le résumé Similarité Gusto compte les variantes sémantiques usuelles une fois par site. L'admin peut lancer « Actualiser le profil visuel » pour refaire uniquement cet appel textuel à partir des analyses de pages stockées, sans nouvelle capture, upload ni appel Vision. Les projets futurs ne reçoivent jamais les captures et ne relancent pas Vision pour le Portfolio.

Le résumé global du Portfolio est calculé localement à partir des sites actifs analysés : nombre de sites, fréquences des tags visuels, motifs fréquents/rares et signatures. Un site est exclu pour le projet courant si `restaurantId` ou `slug` concorde exactement ; une ressemblance de nom ne suffit pas. Si aucun site éligible n'existe, la génération continue avec une diversité générale. Le slider `gustoSimilarity` a désormais un seul sens : **0** demande de s'écarter nettement des motifs fréquents du Portfolio ; **50** autorise une continuité partielle sans répétition automatique ; **100** autorise une forte continuité, jamais la copie d'un site. Le résumé textuel influence directement le prompt Sol, et les références externes reçoivent seulement un faible bonus ou malus de proximité avec les motifs fréquents ; brief, réglages et qualité de la référence restent prioritaires. La précédente pénalité basée sur `DesignReference.useCount` a été retirée du score de sélection.

Pour ajouter un univers, compléter `STYLES` dans `client/src/components/dashboard/admin/sites/design-lab.shared.js` et, si nécessaire, `STYLE_WORDS` dans `design-lab.service.js`. Pour une caractéristique de référence, ajouter la propriété au schéma strict `referenceSchema` dans `openai.service.js` puis adapter le score local et l'affichage si elle doit influencer la sélection.

La création de projets Next.js, le code de homepage, la Visual QA et le déploiement sont réservés à la phase suivante. La future Site Factory pourra lire `approvedSnapshot` uniquement si `status=approved` ; un projet réouvert n'a plus de livraison finale active.

## Design Engine — parcours artistique actuel

Ce parcours est le seul moteur de directions, Style Frames et homepages exécutable. `engineVersion: v2` reste une version technique du contrat stocké ; elle ne sélectionne pas un moteur alternatif. Les anciennes directions et maquettes de benchmark Le Ventadour ont été retirées de MongoDB TEST et leurs images de génération supprimées de Cloudinary.

Le moteur sépare quatre sources : le brief et `existingWebsiteContext` sont documentaires, le Portfolio est une comparaison ou une contre-référence selon `gustoSimilarity`, les DesignReference sont des inspirations visuelles positives, et les assets client représentent le restaurant réel. L'URL de l'ancien site, ses captures, CSS, couleurs et structure n'entrent pas dans le payload artistique. Le brief manuel prime sur le contexte documentaire. À faible similarité, les motifs Portfolio présents sur plusieurs sites deviennent des `divergenceConstraints` explicites ; aucune capture Portfolio n'est fournie à Sol ou au modèle image. Le score local de sélection des DesignReference reste celui déjà en place.

La génération des directions comporte maintenant deux étapes. Un premier appel Sol produit trois **territoires créatifs A/B/C** distincts avec idée de marque, thèse, personnalité, territoires visuel, chromatique, typographique, photographique et spatial, différenciateur et deux ou trois références pressenties. Il reçoit jusqu'à huit références sous une forme compacte : concept, composition, rythme, typographie, palette, photographie, gestes distinctifs et rappel de ne pas copier. Les analyses détaillées restent en base, mais ne sont pas envoyées à cet appel. Le serveur vérifie le contrat structurel et les index des références ; aucun second appel payant n'est déclenché automatiquement. Un résultat techniquement invalide exige une nouvelle reprise manuelle. La proximité artistique des territoires produit un warning sans retry payant.

Les trois **expansions** démarrent ensuite en parallèle. Chacune reçoit son propre territoire, les deux autres comme territoires réservés à éviter, le contexte documentaire et les réglages, la divergence Portfolio, les assets réels et les seules analyses détaillées de ses deux ou trois références pressenties. Le modèle ne peut conserver comme `referenceAnchors` que deux ou trois de ces références, avec raison et principes. Chaque appel d'expansion a son propre Structured Output pour une seule direction. Le parcours normal effectue quatre appels Sol. Une reprise manuelle ne rappelle que les étapes absentes ou toujours invalides du checkpoint compatible. La répétition partielle du contexte et le nombre d'appels augmentent le coût, tandis que les sorties individuelles sont plus petites et les expansions parallèles réduisent le temps mural attendu. Les trois résultats sont vérifiés puis enregistrés ensemble : une expansion échouée ne laisse aucune direction officielle partielle dans le projet, mais les réponses déjà payées sont conservées dans un checkpoint interne masqué. Une diversité finale insuffisante produit un warning non bloquant. Les délais sont de 240 secondes pour chaque tentative de territoires, 480 secondes pour chaque expansion, 17 minutes côté admin pour le pipeline complet et 20 minutes pour le verrou du projet. L'admin voit l'étape réelle `territories`, `expanding` ou `saving`, sans pourcentage simulé.

Chaque Structured Output d'expansion produit `brandSystem`, puis `visualSystem`, puis `siteInformationArchitecture` pour sa direction. Le premier contient `brandIdea`, `brandPersonality`, `colorSystem` (surfaces, accents, textes, traitement photo), voix typographique, formes, photographie, matière, graphisme, iconographie, espace, voix éditoriale et listes `brandDo`/`brandDont`. Chaque rôle couleur inclut nom/hex, fréquence, usage, surfaces, associations, interdictions et provenance (`sourceType`, `sourceExplanation`). Le réglage `brandContinuity` vaut `reinvent`, `evolve` ou `preserve` ; par défaut `reinvent`, la forme du logo peut être conservée sans faire de ses couleurs une contrainte. Le système visuel contient thèse, grammaire de composition, carte de rythme, climats, systèmes photo/typo, gestes signature avec limites explicites, anti-patterns, anchors et divergence. L'architecture de l'information contient `primaryPages`, `homepageRole`, `contentAssignments`, `homepageMoments` (**cinq à sept conseillés**, quatre ou huit acceptés si cohérents) et `dedicatedPageTopics`. Elle classe chaque sujet entre `homepage_primary` (moment autonome et concis, sans page dédiée nécessaire), `homepage_teaser` (aperçu d'un sujet développé sur une page dédiée), `dedicated_page`, `global_navigation`, `footer_only` et `optional`. Chaque moment porte un `placement` primaire ou teaser, cohérent avec tous ses `contentTopics`. `targetPageId` et `destinationPageId` valent `null` sans destination ; un teaser exige le même ID de page dédiée dans les deux champs. La brièveté d'un hero ou manifeste ne le transforme pas en teaser. Les moments décrivent intention, sujets concis, éventuelle destination, priorité, hauteur, climat, surface, composition, intensité et besoins d'assets. Menus/plats/prix, réservation détaillée, traiteur détaillé, formulaires et informations pratiques complètes restent sur leurs pages dédiées si ces services existent. Le contrôle local vérifie les pages de destination, interdit les sujets réservés dans les moments d'accueil, rejette les anchors absentes et couleurs sans provenance. Le nombre de moments hors cible, les répétitions voisines, la faible diversité, les quotas de personnalité/graphisme/signatures et la proximité des directions produisent des `qualityWarnings` non bloquants, journalisés et enregistrés. Aucune alternance ni quantité minimale d'effets n'est imposée. Les rejets d'architecture journalisent le moment, le placement, la destination et un motif structuré sans conserver la réponse OpenAI.

Chaque moment déclare aussi `momentRole`, `contentScope` et `homeElements`. Un teaser a `contentScope: "teaser_only"`, une invitation et un CTA, et `contentIntent: ""` : son expression créative est portée par `editorialIntent` (`kind: invitation`, `headlineIdea`, `tone`, `ctaLabel`, limités à 120/80/60 caractères). Cet objet est nullable pour un primary, obligatoire pour un teaser. Le plan de home conserve cette invitation structurée et utilise le libellé de sa page cible, sans `dedicatedPageTopics` ni sujets exclus. Les éléments fonctionnels déclarés restent interdits ; aucune recherche lexicale n'interprète les headlines. Leur conformité sémantique reste à vérifier humainement. Les moments primaires, hero compris, combinent librement headline, short_copy, photography et cta : au moins une primitive, sans titre ni CTA obligatoire. Les doublons de primitives sont normalisés. La matrice de validation figure dans [DIRECTIONS_V2_CONTRACT.md](./DIRECTIONS_V2_CONTRACT.md). La matrice générative et la reprise checkpointée sont documentées dans [DIRECTIONS_V2_RECOVERY.md](./DIRECTIONS_V2_RECOVERY.md).

Pour chaque direction, l'admin doit générer puis **valider humainement un Style Frame** avant de demander la homepage. Il représente désormais **une tranche web verticale continue de trois moments**, en **1 024 × 1 536 px** : entrée, grammaire intérieure et variation de climat, à une échelle lisible. Les trois moments sont sélectionnés localement depuis la direction ; aucun sujet ni composant récurrent n'est imposé. La sélection, les tentatives, les erreurs et la récupération sont documentées dans [STYLE_FRAME_PIPELINE.md](./STYLE_FRAME_PIPELINE.md). Nouvelle proposition utilise Flare et jusqu'à cinq `CLIENT_ASSET` autorisés plus les deux ou trois images originales des anchors `VISUAL_REFERENCE`. Affiner utilise Sunburst et place le `CURRENT_STYLE_FRAME_TO_REFINE` en première image, suivi des mêmes catégories d'inputs et d'un feedback propre à la tentative (maximum 1500 caractères). Aucun screenshot Portfolio, ancienne homepage ou asset `benchmarkExcluded` n'est envoyé. Chaque action accepte au maximum un appel image, sans retry automatique ni appel Sol/Luna. Les anciens Style Frames restent conservés et valides. La route de homepage refuse une direction sans Style Frame validé (`409`).

Le blueprint part exclusivement des `homepageMoments` de `siteInformationArchitecture` et assigne les assets par besoin de section, rôle et pertinence, avec propriété exclusive par défaut. Une variation reprend le blueprint validé de sa génération parente. Les chapitres reçoivent le Style Frame validé en première image, puis chapitre précédent et bande de raccord le cas échéant, puis les assets de leurs seules sections. Les prompts comprennent `RENDER_ONLY`, `FORBIDDEN_CONTENT`, sections déjà rendues, sections futures, ownership, système de marque, système visuel, architecture de l'information et plan global. Header/hero restent dans le premier chapitre ; footer seulement dans le dernier. La home présente le restaurant et oriente vers les pages dédiées avec des aperçus courts, sans recopier leurs interfaces complètes. Les générations conservent `engineVersion`, `styleFrameId` et le blueprint. Le snapshot final fige direction, brand/visual systems, architecture de l'information, Style Frame validé, blueprint, génération, assets, anchors, références et réglages.

Avant tout appel payant, `npm run design-lab:preview-engine -- <slug> [directionId]` lit **uniquement MongoDB TEST** et affiche le payload exact de l'appel de territoires : contexte documentaire, divergence Portfolio, huit références compactes, assets, instructions, tailles et schéma Structured Output. Elle affiche aussi les gabarits A/B/C des expansions, leur schéma et des estimations illustratives de sortie. Les territoires et références détaillées de chaque expansion sont explicitement marqués comme dynamiques : ils ne peuvent être connus avant le premier appel Sol et ne sont pas inventés par le preview. Si une direction existe déjà, la commande affiche aussi son architecture de l'information, son Style Frame et son blueprint. Elle ne télécharge pas d'image, n'écrit rien et n'appelle pas OpenAI.

### Reprise des directions payées

Les directions officielles sont versionnées dans trois slots principaux **A/B/C**. Un run complet archive l'ancien set et active les trois nouvelles versions ; une régénération remplace seulement la version active de son slot. Images et homepages restent attachées aux versions historiques ; aucune ancienne validation n'est transférée. L'API et l'UI principales filtrent `status=active` et A/B/C. Contrat, sélection et migration ciblée : [DIRECTION_VERSIONING.md](./DIRECTION_VERSIONING.md). Aucune Wildcard n'est implémentée.

`directionGenerationCheckpoint` persiste les territoires et les réponses parsées A/B/C avant validation, hors directions officielles et hors sérialisation API. Une reprise manuelle revalide ces résultats et ne rappelle que les étapes manquantes/invalides. `contractVersion` compare prompts, schémas et modèle ; `contextHash` compare les sources effectives ; le validateur possède une version distincte pour permettre une revalidation locale après correctif. Un checkpoint incompatible est conservé et bloque tout appel (409), jusqu'à son abandon explicite via `DELETE /api/admin/design-lab/projects/:id/directions-checkpoint`. Le save officiel consomme le checkpoint atomiquement avec les directions. Aucun retry OpenAI automatique.
